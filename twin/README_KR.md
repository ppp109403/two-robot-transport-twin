# twin — 두 대 협력 운송을 Isaac Sim 에서 검증하는 리그

MPC 플래너(`~/ros2_ws/src/mobile_manipulator_trajectory`)가 푼 궤적을 Isaac Sim 안에서
**로봇 두 대에 같은 정책을 물려** 재생하고, 추종·결합·충돌을 정량으로 판정한다.

기존 `scripts/eval_plans.py` 와의 차이는 셋뿐이다:

```
1 대 x N env          ->  한 씬에 2 대 (서로를 본다)
빈 평지               ->  실제 SLAM 맵을 2 m 압출한 3D 장애물
독립된 EE 목표        ->  2 m 막대로 묶인 결합 구속
```

---

## 상태

```
Phase 0   완료      정합성 게이트 G1 / G2 / G3 전부 통과 (2026-08-12)
Phase 1   진행 중   씬 완성 (2로봇 + 맵, 스모크 통과). 다음은 30 Hz 재생 루프
Phase 2   대기      막대 결합 B1(스프링댐퍼) -> B2(강체)
Phase 3   대기      로컬라이제이션 현실화
Phase 4   대기      ROS 2 통합 (Track B)
Phase 5   대기      스윕 / 회귀
```

### Phase 0 결과

| 게이트 | 무엇을 | 결과 |
|---|---|---|
| G1 `check_obs_parity.py` | 상태 → 관측 (`ee_obs.py` vs 학습 ObsTerm) | AMCL off 에서 전 블록 **≤ 1e-6** |
| G2 `check_plan_sampler.py` | 계획 보간 (twin vs 플래너 노드 `_sample_step`) | 977점 **오차 0**, 막대 보존 4e-16 m, 실계획 CSV 왕복 통과 |
| G3 `check_plan_target.py` | 계획 → EE 목표 (twin vs 학습 커맨드 term) | pose 2e-6 m / rot6d 5e-7, 선속도 xy 9e-5 |

재현:

```bash
twin/run.sh twin/tools/check_obs_parity.py --amcl on --policy handoff/traj_v29/policy.pt --report /tmp/g1.txt
python3      twin/tools/check_plan_sampler.py
twin/run.sh twin/tools/check_plan_target.py --report /tmp/g3.txt
```

### 액션 적용을 게이트하지 않는 이유

`DiffDriveAction` / `DelayedJointPositionAction` 을 **옮겨 적지 않고 그대로 재사용**하기로
했다. 이 저장소가 반복해서 당한 사고가 "같은 로직 두 벌이 갈라지는 것"이고
(`AmclPoseEstimator` docstring 이 그 상태를 자기 입으로 경고하고 있다), 구현이 하나면
대조할 상대가 없어 게이트 자체가 불필요해진다. Phase 1 의 씬은 그래서 매니저 기반
환경 위에 올린다 — 액션 항·가감속 램프·액션 지연·decimation 을 전부 학습과 같은
코드로 받기 위해서다.

## 로컬라이제이션 — 참값을 쓴다는 것의 의미

학습 커맨드 term(`MovingPoseWorldAmclCommand`)은 목표를 base 프레임으로 옮길 때
**참값이 아니라 AMCL 추정값**을 쓴다. 즉 정책은 "내 위치를 정확히 모른다"는 조건에서
학습됐다. 학습에 쓰인 모델은:

```
pos_noise_std   0.005 m       update_period  0.18 s
yaw_noise_std   0.004 rad     latency        0.06 s
jump_prob       0.002
```

Phase 1 에서 참값을 쓰는 것은 **이 분포의 무잡음 끝**을 쓰는 것이지 분포 밖이 아니다.
다만 그래서 나오는 EE 오차는 **낙관적**이다. Phase 3 는 새 모델링이 아니라 기존
`AmclPoseEstimator` 를 같은 상수로 켜는 일이다.

주의: `ee_pose` 항은 참값 root 기준(=팔 FK)이고 `pose_command` 만 추정값 기준이다.
실기에서도 그래야 AMCL 오차가 두 번 들어가지 않는다.

## Phase 1 결과 — 두 대 동시 재생, **리그 종단 검증 통과**

리그가 검증하려는 것은 **한 씬에 두 대를 올려 각자 자기 궤적을 자기 정책으로 추종**
시키는 것이다. 막대로 묶거나 같은 물체를 나르는 편대가 아니다.

`data/plans.npz` held-out 궤적 두 개(ds[108], ds[113])를 각 로봇에 물리고,
압출한 munji 맵 위에서 v29 를 두 대에 돌린 결과:

```
              EE 중앙    EE 95%    자세 중앙   차체편차 중앙
robot_a       13.68 mm  20.86 mm   5.58 deg     0.466 m
robot_b       12.51 mm  34.55 mm   5.32 deg     0.629 m

매니저 env 기준 (ev_plans_v29.log, 같은 궤적)
ds[108]       13.31 mm  20.41 mm   4.20 deg     0.322 m
ds[113]        9.93 mm  17.18 mm   1.52 deg     0.614 m
```

**EE 오차가 기준과 일치한다.** 씬·관측·액션·보간·목표변환 전 경로가 맞다는 뜻이다.
hold 단계에서도 두 대 모두 2.7 mm / 8.5 mm 로 수렴한다.

### 여기까지 오면서 잡은 버그 — **액션을 자르면 안 된다**

첫 재생은 EE 275 mm 로 발산했다. 원인은 내가 정책 출력을 `clamp(-1, 1)` 한 것이었다.

```
학습의 JointPositionAction:  관절목표 = default + scale * action   ← clamp 없음
관측의 last_action:          action_manager.action = **raw** 값
실측:                        팔 액션의 12~20 % 가 |a| > 0.98
```

즉 ±1 로 자르면 **팔이 뻗을 수 있는 범위가 잘리고**, 그 잘린 값이 관측으로 되먹여진다.
증상은 "팔이 안 뻗고(reach 중앙 0.127 m) 목표에서 점점 뒤처짐"이었다. 차체
(`DiffDriveAction`)는 자기 안에서 `max_lin_vel`/`max_ang_vel` 로 자르므로 그쪽은 무관하다.

가는 길에 기각한 가설들 (전부 원인이 아니었다):

```
맵 압출              --no-map 로 A/B -> 265 vs 278 mm, 차이 없음
로컬라이제이션 지연   AMCL 모델 on/off -> 275 vs 278 mm, 차이 없음
캐스터 감쇠          감쇠 0~1.0, effort 0.5~500 -> 자전에 추세 없음
```

### 부수 관찰 — 협력 운송 편대는 v29 분포 밖이다

(이건 요청한 구성이 아니지만, 초판에서 잘못 만들었다가 얻은 결과라 남겨 둔다.
나중에 편대를 진짜로 하려면 필요한 숫자다.)

계획 `margin_005` (7.0 m, 84.6 s) 를 v29 두 대에 물린 첫 재생 (참값 위치, 막대 없음):

```
            EE 중앙    EE 95%    차체편차 중앙    자세오차 중앙
A          114.5 mm   150.6 mm     0.420 m        16.4 deg
B          688.6 mm   945.2 mm     0.558 m        73.3 deg
학습 기대    9.5 mm    17.1 mm     0.501 m         1.7 deg
막대 길이 오차 중앙 688.8 mm,  로봇 최소간격 0.813 m (제한 0.90)
```

원인은 정책 성능이 아니라 **계획이 요구하는 것이 학습에 없다**는 것이다.

**[1] 팔이 만들어야 하는 상대 요가 분포 밖**

`막대방향 − 차체요` 의 분포:

```
학습 (plans.npz)   중앙  -4.3 deg   5~95% [ -65,  +64]   |>60deg| 13.1%
계획 A             중앙 +57.6 deg   5~95% [-165, +154]   |>60deg| 45.1%
계획 B             중앙 +71.1 deg   5~95% [ +26,  +92]   |>60deg| 61.1%
```

**[2] B 는 주행의 86% 를 후진해야 한다**

```
계획 base_A  전진성분 중앙 +0.086 m/s   후진 비율   0.0%
계획 base_B  전진성분 중앙 -0.075 m/s   후진 비율  85.9%
```

`two_robot_nlp.py` 가 주석에 적어 둔 그대로다 — *"one robot leads the bar and
therefore drives in reverse the whole way"*. 그런데 v29 는 `max_reverse_vel 0.2`
(전진 0.5) 에 **후진 벌점**(`base_reverse`)까지 걸고 학습했다. 실제로 시뮬의 B 는
계획이 후진을 요구하는 구간에서 **82% 를 전진**한다 — 계획을 안 따르는 것이다.
그 결과 목표가 리치 밖으로 밀려난다 (B: 목표까지 차체거리 중앙 0.768 m,
**64% 가 reach_max 0.60 초과**).

**[3] EE 가 차체 뒤에 오는 비율도 3~5 배**

```
학습 4.9%   계획 A 23.2%   계획 B 14.0%
```

### 그래서 무엇을 해야 하나

정책을 더 돌리는 것으로는 안 된다. **학습 데이터를 편대 계획으로 바꿔야 한다** —
지금 `plans.npz` 는 단일 로봇 MPC 주행에서 뽑은 것이라 편대 기하(마주 보는 두 대,
한 대는 후진)가 아예 들어 있지 않다. `twin/tools/solve_plan.py` 가 헤드리스로
두 대 계획을 풀 수 있으므로, A 역할과 B 역할을 각각 궤적으로 뽑아 재학습 데이터로
쓰는 것이 다음 수순이다. 후진 벌점도 B 역할에는 빼야 한다.

증거로 남은 것: B 는 계획이 목표에 정착하는 마지막 20% 구간에서 **2.94 deg / 18.8 mm**
까지 수렴한다. 즉 정책이 못하는 것이 아니라, 편대가 요구하는 **동적 구간**을 못 따라간다.

## Phase 0 이 찾아낸 것 — 미해결 두 건

### (1) `target_vel` 피드포워드 채널이 학습·실기·twin 셋 다 다르다

G3 이 찾았다. 목표 pose 는 세 경로가 1e-6 로 일치하는데, 속도 채널은 아니다:

```
학습 env    _update_command 가 기하 합성 경로를 전체 env 에 먼저 돌리고,
            _update_from_plan 이 그 위에 pose 와 lin xy 만 덮어쓴다.
            -> 계획 env 의 ang 과 lin z 는 계획과 무관한 잔여값.
               실측 ang 중앙 0.257 rad/s, lin z 95% 0.054 m/s
실기 브리지  plan_adapter.py 가 계획에서 유도한다 (ang z = 목표 요 변화율, lin z = 0)
twin        ff_mode 로 고른다. 기본 planner (실기와 같게)
```

정책이 이 채널을 무시하도록 학습됐을 가능성이 높다 — 계획 env 에서 그 값이 계획과
무상관한 잡음이었고, 실기가 다른 값을 넣는데도 예측대로 동작해 왔다. **다만 확인된 적이
없다.** Phase 1 에서 `ff_mode=planner` 와 `zero` 를 같은 계획으로 돌려 EE 오차가
갈리는지 보면 끝난다. 갈리면 재학습 항목이고, 안 갈리면 그냥 지워도 되는 채널이다.

### (2) `base_margin >= 0.70` 은 munji 맵에서 성립하지 않는다

`twin/world/map_extrude.py` 가 시뮬을 짓기 전에 답을 냈다. 필요 SDF 여유는 margin 이
아니라 **디스크반경 + margin** 이다 (base 디스크 r = 0.306 m).

```
주행 가능 영역 265.6 m^2,  여유거리 중앙 0.57 m

margin   필요여유    면적%   최대성분(성분수)   판정
 0.05    0.356 m    68.4%   178.3 m^2 ( 2)    연결 양호
 0.20    0.506 m    55.3%   122.4 m^2 ( 3)    분절 주의
 0.30    0.606 m    46.8%   102.7 m^2 ( 5)    분절 주의
 0.50    0.806 m    32.4%    21.3 m^2 (11)    분절 심함
 0.70    1.006 m    19.8%    15.3 m^2 (21)    분절 심함   <- v29 요구치
```

면적이 아니라 **연결성**이 문제다. margin 0.70 에서는 265 m² 가 21 조각으로 끊기고
가장 큰 조각이 15 m² 라 방 사이를 갈 수 없다. 즉 v29 의 차체 편차(중앙 0.50, 95% 0.65)를
플래너 여유로 흡수하는 전략은 **이 맵에서는 불가능**하다.

이게 사실이면 v29 vs v12~v28 의 교환관계가 다시 보인다:

```
      EE 중앙    차체 편차 중앙    필요 margin    이 맵에서
v29    9.5 mm       0.501            ~0.50        불가
v12   13.9 mm       0.311            ~0.31        경계
v28   31.8 mm       0.094            ~0.09        여유
```

**플래너를 실제로 돌려 확인했다** (2026-08-12, `twin/tools/solve_plan.py`).
같은 시작·목표(측지 7.0 m 경로), 같은 v29 프로파일, `base_margin` 만 바꿨다:

```
margin   IPOPT s   최소여유   목표오차   동역학잔차   판정
 0.05      194.5   +0.049     0.000     1.4e-05    성립
 0.20     1197.3   +0.049     0.000     7.0e-05    성립
 0.30       89.2   +0.049     0.000     4.0e-05    성립
 0.50      134.2   +0.061     0.369     5.7e-01    IPOPT 미수렴
 0.70      323.5   +0.050     0.767     2.5e+00    IPOPT 미수렴
```

0.50 / 0.70 은 마지막 반복치일 뿐 해가 아니다 — 목표에 0.37 / 0.77 m 못 미치고
동역학 잔차가 0.57 / 2.5 라 유니사이클로 **주행 자체가 불가능**하다.

**맵 분석의 예측이 그대로 맞았다.** 이 경로에서 성립 상한은 `base_margin ~0.30`,
v29 가 요구하는 것은 ~0.50. 격차가 실측으로 확인됐다.

남은 것은 정책의 편차가 **벽 쪽인지 열린 쪽인지**다. 편차가 통로 중앙 쪽으로만
생긴다면 margin 을 덜 잡아도 될 수 있다. Phase 1 이 이 맵 위에서 실제로 소진된
여유를 재면 끝난다.

(주의: 이건 **한 경로** 결과다. 7 m 짜리 통로 하나를 지나는 계획이고, 다른 경로는
더 관대하거나 더 빡빡할 수 있다. 맵 전체 연결성 표가 그 분포를 말해 준다.)

### (3) v29 프로파일에서 한 판이 갈 수 있는 거리는 8.3 m 다

`twin/tools/solve_plan.py` 를 짜면서 드러났다. 지평선 예산은

```
(max_steps - n_settle) * dt * v_nom / horizon_slack
= (700 - 12) * 0.15 * 0.10 / 1.25  =  8.3 m
```

이 맵의 주행 가능 영역은 측지 지름이 **71.7 m** 다. 즉 v29 권장 속도
(`obj_v_max 0.12`)로 건물을 가로지르려면 `max_steps` 를 6000 가까이 올리거나
계획을 **구간으로 쪼개야** 한다. 기본값 700 으로는 한 판에 8 m 다.

관련해서, 2 m 막대가 **어떤 요로든 들어가는** 자리는 주행 가능 영역 265.6 m² 중
**177.0 m²** (67%) 뿐이다. 시작·목표 자세는 하드 제약이므로 나머지 33% 에는
애초에 물체를 놓을 수 없다.

### (4) 이 맵에서는 `unknown_is_occupied` 가 무효다

맵의 **90.96 % 가 픽셀 205(미지)** 인데 yaml 의 `free_thresh: 0.25` 가 그것을
자유공간으로 만든다 (205 의 점유도 0.196 < 0.25). ROS `map_server` 규칙상
`/map` 에 **-1 이 하나도 실리지 않으므로**, 플래너의 `unknown_is_occupied: True` 는
이 맵에서 아무 일도 하지 않는다. A\* 가 건물 바깥 미지영역을 가로지르는 계획을 낼 수 있다.

이건 시뮬 문제가 아니라 **실기 플래너 설정 문제**다. `free_thresh` 를 0.196 이하로
내리면 해결된다. twin 은 우회하지 않고 원본 pgm 에서 직접 분류한다.

### (5) 명령 0 인데 차체가 초당 3.6 도씩 자전한다 (학습 env 도 동일)

Phase 1 씬 스모크가 찾았다. 액션을 0 으로 두고 가만히 두면 차체가 계속 돈다:

```
twin (2로봇, 계획 자세)     A 8.4 deg/s   B 4.5 deg/s
학습 env (v29 Play, 4 env)  중앙 3.6 deg/s  (2.6 ~ 5.7)
```

**twin 의 버그가 아니다.** 같은 에셋·같은 액션 설정이라 학습 env 에서도 같은 폭으로
돈다. 원인은 캐스터 설정이다 (`ee_track_ppo/assets/amr_fr3.py`)::

    casters: stiffness 0, damping 0, velocity_limit 200 rad/s

캐스터 바퀴가 **저항 없이 상한 200 rad/s 로 계속 회전**하고, repo 기록대로 캐스터가
2 mm 떠 있으면 차체는 구동륜 두 점으로만 지지되어 요 방향 저항이 거의 없다.

왜 중요한가 — **v29 의 미해결 항목과 연결될 수 있다.** v29 handoff 가 못 잡았다고
적은 것이 "속도 출렁임 0.0593 (기준 0.010), 부호 반전 1.22 회/초" 였다. 정책이
**시뮬에만 있는 자전을 상시 상쇄하도록 학습됐다면**, 그 상쇄 동작이 실기에서는
불필요한 좌우 진동으로 나타난다. 실기 바퀴는 정지 시 잠기므로 자전이 없다.

아직 가설이다. Phase 1 에서 차체 지령의 부호 반전이 자전 보상과 상관되는지 보면
검증된다. 맞다면 고칠 곳은 정책이 아니라 **캐스터 damping** 이다.

### (6) AMCL 요 지연이 문서가 말하는 것보다 훨씬 크다

G1 이 `--amcl on` 에서 잰 `target_vel` 이음매 (6320 표본):

```
중앙 3.3e-3    95% 2.6e-2    최대 1.1e-1  [m/s]
```

`ee_obs.py` 는 이 이음매를 "정상상태 잡음 0.004 rad → 약 0.2 도" 로 적어 두었는데,
실제로는 **갱신주기 0.18 s + 지연 0.06 s 동안의 요 지연**이 지배하고 최댓값은
AMCL 점프(`jump_yaw_std` 0.10 rad)다. 지연을 줄이려고 넣은 피드포워드 채널에
최대 0.1 m/s 오차가 실린다는 뜻이라 실기에서 볼 값이다.
