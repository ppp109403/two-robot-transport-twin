# 차체 추종을 보상에 넣으면 왜 무너지는가

> **학생들이 얻은 결론:** "베이스 추종을 리워드에 넣으면 무너짐. 엔드이펙터 추종까지는 괜찮음."

**이 결론은 맞다.** 그리고 이 저장소는 같은 것을 **여섯 판에 걸쳐 독립적으로 실측**해
두었다. 아래는 그 기록과, 원인 분석, 그리고 다음에 시도할 것들이다.

---

## 1. 실측 — 차체를 조일수록 EE 가 나빠진다

같은 시험대(실제 플래너 궤적 24 개 held-out, EE 목표 높이 0.55 m, 같은 도구):

| 판 | 차체 참조 보상 | EE 평균/중앙 [mm] | EE 자세 중앙 [deg] | 차체 편차 중앙 [m] | 3 cm 통과 |
|---|---|---|---|---|---|
| **v2** | **없음** | **8.6 / 8.0** | **1.21** | 0.437 | **92 %** |
| v12 | tanh, w 0.35 | 13.9 | 10.5 | 0.240 | 84 % |
| v17 | 밴드(불감대) | 31.4 / 34.2 | 3.00 | 0.126 | 33 % |
| v28 | 밴드 | 41.7 / 31.8 | 2.08 | 0.130 | 25 % |
| v24 | 밴드 + 자세칸 | 105.1 / 112.7 | 2.89 | 0.117 | 17 % |
| **v29** | **없음 (안정항만)** | **10.1 / 9.5** | 1.72 | 0.495 | **88 %** |

읽는 법: **차체 편차가 좋아지는 순서와 EE 가 나빠지는 순서가 정확히 반대다.**
0.437 → 0.240 → 0.126 → 0.130 → 0.117 로 차체가 3.7 배 좋아지는 동안,
EE 는 8.6 → 105.1 mm 로 **12 배** 나빠졌다.

더 날카로운 두 번째 표 (`base_ref_error_band` 의 docstring 기록):

| 판 | 차체 가중치 | 차체 편차 [m] | EE 자세 오차 [deg] |
|---|---|---|---|
| v6 | 0.15 | 0.488 | 3.3 |
| v12 | 0.35 | 0.240 | 10.5 |
| v15 | 0.50 + 속도항 | **0.062** | **53.4** |

**차체를 13 배 좋게 만드는 대가가 자세 16 배였다.** 이건 잡음이 아니라 단조 교환관계다.

## 2. 원인 — 보상 설계 문제가 아니라 **기구학적 갈등**이다

핵심 한 줄:

> **차동구동은 옆으로 못 간다. 6축 팔이 만들 수 없는 EE 자세는 차체가 자리를 옮겨서
> 만들어야 한다. 차체 참조 보상은 정확히 그 동작을 금지한다.**

풀어서:

- 모바일 매니퓰레이터는 **여유 자유도(redundant)** 시스템이다. EE 6 자유도를 맞추는 데
  팔 6 + 차체 2(비홀로노믹) = 8 이 있다.
- 그 여유분은 낭비가 아니라 **팔의 자세를 좋게 만드는 데 쓰이는 자원**이다.
  팔이 특이점 근처거나 관절 한계에 걸리면, 차체가 몇 십 cm 옮겨서 팔에게 좋은
  자세를 만들어 준다.
- 차동구동은 **횡방향 순간 속도가 0** 이다. 옆으로 20 cm 가려면 돌고-전진하고-되돌아야
  한다. 즉 차체의 "자리 옮기기" 는 항상 참조 경로에서 **크게** 벗어나는 형태가 된다.
- 차체 참조 보상은 그 이탈을 벌한다. 그러면 정책은 팔만으로 어떻게든 해보려 하고,
  팔이 못 만드는 자세는 그냥 포기한다.

**차체가 참조에서 벗어나던 것은 실패가 아니라 자세를 맞추려는 시도였다.**
그것을 막으니 자세가 무너진 것이다.

### 왜 "EE 추종까지는 괜찮은가"

EE 위치는 여유가 크다. 팔 하나만으로도 대충 닿는다. 그래서 차체를 묶어도 위치는
버틴다. 무너지는 건 **자세**다 — v15 에서 위치는 살아 있는데 자세가 53.4° 였다.

**그래서 학생들에게 확인할 첫 번째 질문:**
"무너진다" 는 것이 EE **위치**인가 **자세**인가? 자세를 따로 로깅하고 있는가?
이 저장소의 기록으로는 **자세가 먼저, 그리고 훨씬 크게** 무너진다.

## 3. 이미 시도했고 실패한 것 — 같은 길을 다시 가지 말 것

| 시도 | 판 | 결과 |
|---|---|---|
| 가중치를 낮춘다 | v6 (0.15) | 차체 0.488 — 사실상 안 따라감. 낮추면 효과가 없고 올리면 EE 가 죽는다 |
| 가중치를 올린다 | v9 (0.60) | EE 자세 0.05 → 0.166 rad (3 배 악화) |
| 위치 낮추고 방위 추가 | v10 (0.35 + 0.20) | 개선 없음 |
| 속도 항까지 추가 | v15 (0.50 + 속도) | 차체 0.062 로 최고, **자세 53.4°로 최악** |
| **불감대(밴드)** | v17 / v28 / v24 | EE 31 / 42 / 105 mm. 밴드도 못 살렸다 |

**밴드가 실패한 것이 특히 중요하다.** "정확히 따라가라" 대신 "이 반경 안에만 있어라"
로 바꾸면 될 것 같지만, 실측은 아니었다. 다만 정직하게 말하면 v17/v24/v28 은
자세 큰오차 칸 등 **다른 변경이 섞여 있어서** 밴드 단독의 효과가 완전히 분리되진
않았다. "밴드도 안 된다" 보다는 "밴드로도 이 정도로는 못 살린다" 가 정확하다.

### 놓치기 쉬운 함정 — 위치만 보상하고 방위를 빠뜨림

v9 에서 관측된 것:

```
base_ref_error       0.33 -> 0.025 m      위치는 잘 따라감
base_ref_yaw_error   1.54 ~ 1.78 rad      전혀 안 따라감
```

`base_ref_error_tanh` 는 **위치 거리만** 본다. 방위는 관측과 지표에는 있었는데
보상에 없었다. 평균 오차 1.6 rad 은 균등랜덤 yaw 의 기대값 π/2 = 1.57 과 거의 같다
— **리셋 때 뽑힌 랜덤값 그대로**였다는 뜻이다.

학생들이 "차체 추종을 넣었다" 고 할 때, 위치만인지 방위까지인지 확인할 것.

## 4. v29 의 해법 — 참조를 버리고 "지그재그만" 직접 벌한다

차체 참조를 완전히 빼고, 대신 **참조 없이 차체 안정만** 잡는 항 넷:

```python
base_ang_accel    -0.30    각속도의 한 스텝 변화량 제곱   ← 핵심
base_action_rate  -0.06    차체 지령 변화율
base_ang_vel      -0.03    각속도 크기
base_reverse      -0.08    후진 비용
```

**각가속도가 핵심이다.** 지그재그는 각속도의 **부호가 자주 뒤집히는 것**이지 크기가
큰 것이 아니다. 각속도 자체를 크게 벌하면 필요한 선회까지 굼떠진다.

결과: EE 9.5 mm (v2 급) + 90° 규약 문제 해결, **600 iteration 만에** (v28 은 3000
돌고도 41.7 mm).

### 그러나 공짜가 아니다 — 문제가 플래너로 이동했을 뿐

```
차체 편차 중앙 0.501 m,  95 % 약 0.65
-> 플래너 base_margin 을 0.70 m 이상 잡아야 장애물 여유 보장이 넘어온다
```

그런데 munji 맵에서 `base_margin 0.70` 은 **성립하지 않는다**:

```
margin   필요여유    면적%   최대성분(성분수)
 0.18    0.486 m    ~57%    ~130 m^2 ( 3)     실제로 쓰는 값
 0.30    0.606 m    46.8%   102.7 m^2 ( 5)
 0.70    1.006 m    19.8%    15.3 m^2 (21)    <- 21 조각. 방 사이를 못 간다
```

IPOPT 로도 확인했다 — margin 0.50 / 0.70 은 미수렴이고, 목표에 0.37 / 0.77 m 못 미치며
동역학 잔차가 0.57 / 2.5 라 유니사이클로 **주행 자체가 불가능**하다.

**즉 v29 는 "해결" 이 아니라 "비용을 다른 곳으로 옮긴 것"** 이다. 그리고 옮긴 곳에서도
비용을 못 낸다. 이게 지금 이 프로젝트의 진짜 미해결 문제다.

## 5. 다음에 시도할 것 — 우선순위 순

### ★ A. 참조를 "경로" 가 아니라 "맵 제약" 으로 바꾼다 (가장 유망)

**논리:** 플래너가 실제로 보장하는 것은 **정확한 경로**가 아니라 **장애물 여유**다.
그런데 지금 보상은 경로를 추종하게 한다. 목적과 수단이 어긋나 있다.

밴드도 결국 "참조 중심의 원" 이라 같은 문제를 안고 있다 — 참조가 통로 한가운데에
있다는 보장이 없다.

**대신:** SDF 클리어런스를 직접 보상/종료 조건에 쓴다.

```
지금:   reward -= f(‖base − base_ref‖)          참조에서 멀면 벌
제안:   reward -= f(clearance_threshold − sdf(base))   벽에 가까우면 벌
```

차체는 통로 안에서 **어디든 자유롭게** 움직일 수 있고, 벽에 다가갈 때만 벌받는다.
팔이 필요로 하는 자유도를 뺏지 않으면서 안전은 보장된다.

- 필요한 것: 학습 씬에 SDF. 이미 `planner/mobile_manipulator_trajectory/sdf_utils.py`
  가 있고 twin 이 압출한 맵도 있다.
- 부수 효과: 플래너 `base_margin` 을 크게 잡을 필요가 없어진다 → margin 0.18 로도
  안전 보장이 성립할 수 있다.
- 비용: 학습 씬에 맵을 넣어야 하므로 무거워진다. 맵 여러 장으로 일반화도 필요.

### ★ B. 먼저 측정 — 이탈이 벽 쪽인가 열린 쪽인가

A 를 하기 전에 **한 가지 사실만 확인하면 판단이 크게 달라진다.**

차체가 계획에서 0.50 m 벗어난다는 건 알지만, **어느 방향으로** 벗어나는지는 아직
안 쟀다. 통로 중앙 쪽(열린 쪽)으로만 벗어난다면 지금도 이미 안전하고,
`base_margin` 을 크게 잡을 필요가 애초에 없다.

```bash
# twin 리그가 이걸 잴 수 있다. 실행 궤적의 실제 SDF 클리어런스를 계획과 비교
twin/run.sh twin/runner/run_episode.py --track-a ... --out .../devcheck --report ...
# log.npz 의 base_a / base_ref_a 와 SDF 를 대조
```

**비용이 거의 0 이고 결론을 크게 바꾼다. 이것부터 하자.**

### C. 비대칭(one-sided) 벌점

B 의 결과가 "벽 쪽으로도 벗어난다" 면: 참조 대비 **벽 쪽 이탈만** 벌하고 열린 쪽
이탈은 자유롭게 둔다. 밴드의 개선판이되 방향을 아는 밴드다.

### D. 보상이 아니라 **관측**에만 남긴다 (미검증 구간)

v6~v28 은 관측(58차원)에도 보상에도 있었고, v29 는 **둘 다** 뺐다.
"관측에는 있고 보상에는 없는" 조합은 **한 번도 시험되지 않았다.**

정책이 "참조가 저기 있다" 는 걸 알되 강제받지 않으므로, 특별한 이유가 없을 때는
자연히 참조 근처에 머무를 수 있다. **비용이 매우 낮은 실험이다** (v29 에 관측 항만
되살리면 됨). 안 되면 바로 버리면 된다.

### E. 스칼라 가중합을 버리고 제약 최적화로

지금은 `EE 보상 + w × 차체 보상` 형태라 두 목표가 **직접 경쟁**한다. w 튜닝은
본질적으로 이길 수 없는 게임이다 (여섯 판이 그 증거다).

대신 제약으로:

```
maximize  EE 추종        subject to   차체 편차 < d
```

Lagrangian PPO / CPO 계열이면 λ 를 자동으로 조절한다. "차체 편차 0.30 m 이내" 라는
**운용 요구를 직접 쓸 수 있다**는 게 큰 장점이다.

- 비용: 알고리즘 교체. rsl_rl 로는 바로 안 되고 구현이 필요하다.

### F. Residual RL — 구조로 푼다

차체 지령을 정책이 처음부터 만들지 말고:

```
cmd_vel = 저수준_경로추종기(base_ref)  +  정책이 내는 보정량
```

기본값이 "참조 추종" 이고, 정책은 필요할 때만 이탈 비용을 지불한다. 지금과 정반대의
기본값이다.

- 비용: 액션 공간·관측 재설계. 큰 변경.

### G. 갈등의 근원을 줄인다 — 기구 쪽 해법

갈등은 "6축 팔이 만들 수 없는 자세" 에서 나온다. 팔이 커버하는 자세 범위가 넓어지면
차체가 움직일 이유 자체가 줄어든다.

이 저장소에 이미 도구가 있다:

```
scripts/mount_height_sweep.py     마운트 높이 스윕
scripts/check_mount_angle.py      마운트 각도
scripts/pitch_height_tradeoff.py  피치-높이 교환관계
scripts/find_shell*.py            도달 가능 껍질
scripts/reach_decompose.py        도달 분해
```

`reach_max 0.60` 인데 실측 도달이 0.70 이다. 마운트를 바꿔 이 여유를 자세 쪽으로
돌릴 수 있는지 볼 가치가 있다.

## 6. 요약

```
관찰       차체 추종을 보상에 넣으면 무너진다             <- 맞다
근거       여섯 판 단조 교환관계 (EE 8.6 -> 105 mm)
원인       기구학적 갈등. 비홀로노믹 차체 + 여유자유도.
           차체 이탈은 버그가 아니라 팔을 위한 자원이다
먼저 무너지는 것   EE 자세 (위치가 아니라)
이미 실패   가중치 조절, 방위 추가, 속도 항, 불감대(밴드)
현재 해법   v29 — 참조를 버리고 각가속도로 지그재그만 벌점
그 대가     차체 편차 0.50 m -> 플래너 여유 0.70 필요 -> 이 맵에서 불가능
다음        [B] 이탈 방향부터 측정  ->  [D] 관측만 남기기(저비용)
            ->  [A] 경로 대신 맵 클리어런스  ->  [E] 제약 최적화
```

**한 문장으로:** 차체를 경로에 묶으려 하지 말고, **벽에서 떨어져 있게만** 하라.
플래너가 보장하는 것도 원래 그것이다.
